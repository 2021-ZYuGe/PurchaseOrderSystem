# Design

## Context

现状与动机见 `proposal.md`。设计需要满足的硬约束：

- 十多名同事各自解压、各自独立，没有服务器、没有共享盘、没有账号体系
- Windows + 便携 Python 3.13，离线可用，同事侧不装 Node、不装 Python
- `purchase.db` 结构 v3、962 条历史下单、671 份合同台账、536 张图片必须原样保留
- 维护者只有一人，改动需要可回退

## Goals / Non-Goals

**Goals:**

- 功能等价：除明确删除的遗留入口外，v2 的行为与输出和 v1 一致
- 结构可预测：目录、模块、接口、字段命名有统一规则，新增功能知道该放哪
- 单机可维护：不引入外部服务、不做数据迁移、不依赖构建产物之外的运行时
- 可回退：v1 的发布包在整个改造期间保持可用

**Non-Goals:**

- 不做多人共享、服务端部署、权限与登录
- 不重写合同模板填充算法，不改付款阈值等业务规则
- 不引入 ORM、TypeScript、SSR、微服务
- 不追求 100% 测试覆盖，回归以文档快照比对为主

## Decisions

### 1. 保留 Python 单机服务，引入 Flask 承载 HTTP

现状是 636 行的自研 `BaseHTTPRequestHandler`，路由、静态、媒体、SSE、错误处理混在一起。改用 Flask 后，路由声明、参数解析、错误处理、静态文件由框架负责，handler 只保留业务调用。

备选是继续用标准库、自己写一层 router：少 5 个依赖，但错误信封、静态缓存、请求解析都要自己维护。考虑到改造目标就是"规范"，选择 Flask；5 个包均为纯 Python，总体积约 3MB，对 53MB 的运行时无感。

单实例、端口探测、窗口关闭后自动退出这些与框架无关的逻辑保留在 `app/api/server.py`，不放进 Flask。

### 2. 一次切换，不做长期兼容层

目录改名影响所有 import，接口改名影响所有前端调用。如果分四次做，中间态需要同时维护中文/英文两套路径和两套字段，成本高于收益。

做法：在 `rewrite` 分支上一次性切换，`main` 上的 v1 继续可运行；切换完成后合并。v1 的发布包另存一份，作为同事侧的回退。

### 3. 前端用 Vite + Vue 3 单页应用（hash 路由）

四个页面共享产品库、供应商列表和系统状态，SPA 只 bootstrap 一次；hash 路由不需要服务端 rewrite，静态托管最简单；构建产物 `web/dist` 提交进仓库，发布与同事侧都不需要 Node。

备选一：多页 + 组件，保留现有 URL，但每页仍要重复拉取基础数据。
备选二：无构建的 ESM + 模板字符串，不需要 Node，但模板写在字符串里，失去 SFC 的结构感，与"更规范"的目标相反。

选择 Vite，并约定：构建产物必须比源码新，`build_release.py` 校验，避免改了源码忘了构建。

### 4. 依赖方向固定为 api → services → domain / infra

- `api` 只做参数解析、调用服务、序列化响应
- `services` 编排用例（生成合同、批次导入、备份）
- `domain` 纯逻辑，不碰数据库和文件（合同模板填充是唯一例外，它必须写 docx）
- `infra` 只碰 IO：SQLite、文件、日志、媒体
- SQL 只允许出现在 `infra/repositories/`，`services` 不写 SQL

这样拆分后，`store.py` 的 1721 行按聚合拆成 catalog / suppliers / contracts 三个 repository，schema 与迁移单独成文件。

### 5. 导入管道进程内化

现状：`import_service` 起子进程跑 `合并新合同.py`，后者再起子进程跑 `_工具_生成数据库.py`，进度靠正则匹配中文日志，stdout 还要 UTF-8/GBK 双解码。

改为：`domain/parser.py` 负责 docx → 结构化数据，`domain/merge.py` 负责增量合并，`import_service` 在同一进程内依次调用，进度用回调函数上报。子进程只保留给构建、维护这类外部工具。

收益是错误可捕获、进度准确、没有编码问题；代价是解析器与合并逻辑必须原样搬过来，所以第 4 组任务先用 `tools/docx_diff.py` 对同一批合同做新旧输出比对，确认一致后再删旧脚本。

### 6. 数据与产物分离

```
data/
  purchase.db     业务库
  media/          产品图片
  output/         生成的合同与信息表
  backups/        每日备份
  logs/           运行日志
  imports/        导入批次
  _archive/       旧 JSON、旧模板等只读归档
```

程序目录只读，升级整体替换。`output_dir` 允许在设置里改到共享盘，但只影响新文件，不迁移旧文件。

### 7. 命名与语言边界

- 目录、文件、模块、函数、变量、类、API 字段：英文
- 中文只出现在三类位置：界面文案、合同正文、业务数据值（供应商名、产品名、备注）
- 注释与 docstring 保留中文，服务维护者阅读
- JSON 统一 snake_case，与数据库列名一致，减少映射层
- 生成的合同文件名保留中文，那是业务内容

### 8. 清理策略分三档

- 程序垃圾（测试、构建产物、一次性脚本、兼容 shim）：直接删
- 有副本的资产（`web/图片` 536 张与 `data/media` 完全一致）：归档后删
- 用户数据（旧 JSON、旧模板）：只移到 `data/_archive/`，物理不删

保留 `tools/docx_diff.py` 作为唯一的回归手段：它不是测试框架，而是"改完合同逻辑，新旧两版逐段比对"的工具。

### 9. 安全与单实例

- 只监听 `127.0.0.1`，不对局域网开放
- 同目录复用一个实例；不再结束其它目录的进程（v1 的 `take_over_others` 在共用电脑时会互相踢）
- 易快报 accessToken 只存在请求内存，不落盘
- 生成的 docx 通过后端受控路由读取，不把 `data/output` 直接暴露成静态目录

### 10. 入口用快捷方式，退出靠页面心跳

沿用 v1 的使用形态：程序根目录放 `采购下单系统.lnk`，目标为 `runtime\pythonw.exe -m app`，工作目录是程序根，图标用 `app.ico`，同时写入相对路径，整个文件夹搬走后仍能解析。`pythonw` 不弹控制台，同事看到的就是一个图标，双击即用。

自动退出用 SSE 心跳，不靠轮询：页面连 `/api/events/alive?id=<页签id>`，关闭时用 `sendBeacon` 调 `/api/events/bye`；服务端在最后一个连接断开后等待 10 秒确认再退出。刷新会在宽限期内重连，不会误退；浏览器被强杀时连接也会断，同样能退出。

备选方案：轮询 `/api/ping`（实现简单，但页面崩溃后要等更久、请求也更频繁）；常驻进程只靠 `stop.bat` 关闭（同事容易忘记，留下后台进程）。选 SSE 是因为 v1 已经验证过，断开是即时事件，代价只是一个长连接。

`start.bat` 保留为排错入口，能看到控制台报错；日常不使用它启动。快捷方式本身不提交仓库：`.lnk` 是二进制且内含绝对路径，由 `build_release.py` 在暂存目录调用 `make_shortcut.py` 现场生成，保证包内路径正确；解压后若丢失或指错，`maintenance.bat` 可一键重建。

## Risks / Trade-offs

- **合同生成回归**：解析器与填充逻辑搬家容易出细微偏差 → 先冻结 3 份基线（主合同、信息表、订购清单），改造后用 `docx_diff.py` 逐段比对，差异必须为零
- **接口改名期间前端不可用**：后端与前端必须同批切换 → 在分支上完成，`main` 的 v1 包继续日常使用
- **Flask 依赖缺失**：便携运行时是复制来的，可能漏包 → 启动时显式 import 校验，`build_release.py` 增加依赖冒烟检查
- **目录改名打断 git 历史**：用 `git mv` 逐文件移动，保留 blame；改名与逻辑改动分开提交
- **数据归档误删**：`data/_archive` 只移动不删除 → 动手前先手动备份 `purchase.db`，归档后核对产品数与图片数
- **构建产物与源码不同步**：改了 `web/src` 忘记 `npm run build` → 发布脚本比较 `dist` 与 `src` 的最新修改时间，过期则拒绝出包
- **快捷方式失效**：部分解压工具会丢 `.lnk`，安全软件也可能拦截 → 包内保留快捷方式、写入相对路径，并提供 `maintenance.bat` 一键重建
- **心跳误判导致误退**：休眠唤醒、网络切换会让长连接短暂断开 → 保留 10 秒宽限期，且只有在“曾经有页面连过、当前连接数为 0”时才退出

## Migration Plan

1. 冻结：给当前提交打 `v1` tag，导出发布包存到项目外
2. 在 `rewrite` 分支按 `tasks.md` 顺序执行
3. 每完成一组任务，跑一次冒烟：双击快捷方式启动、搜索、生成合同、导入一份合同，关掉页面确认进程退出
4. 全部完成后用两台机器解压试用，确认数据保留与升级路径
5. 合并回主分支，旧目录保留一周再清理

回退方式：任何阶段出问题，直接用 `v1` 发布包恢复；`data/` 全程未被修改，回退不需要数据迁移。

## Open Questions

无。输出目录默认值与是否显示数据位置都可以在实现时按体验微调，不影响规格与任务拆分。
