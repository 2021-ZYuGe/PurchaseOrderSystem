# Design

## Context

动机见 `proposal.md`。影响方案落地的现状与约束：

- 合同台账 `contracts` 只有供应商，没有甲方；`supplier_contract_stats()` 按供应商汇总，并取该供应商所有合同里最晚的止日。
- 甲方信息目前硬编码在 `web/src/pages/ContractPage.vue`，只用于生成主合同；订购清单在浏览器端生成，甲方名称同样写死。
- 供应商名称以原始字符串作为 `suppliers.name` 唯一键；解析时 `re.split(r"[\s　]", ...)[0]` 按空格截断。
- 历史合同文件仍在 `C:\Users\PC\Desktop\合同下载`：673 个文件（645 docx + 28 doc），文件名含易快报单号。
- 数据库结构 v3，迁移机制为 `schema_migrations`，迁移前自动整库备份；升级后旧程序拒绝打开新结构。
- 维护者一人，改动必须可回退；`data/` 是真实业务数据。

只读核查结果（用于确定迁移策略）：

- 按单号匹配：671 / 694 份合同能找到文件。
- 逐份读正文识别甲方：兴趣岛 625 份、普惠 13 份、未识别 33 份、无文件 23 份，共 56 份需要人工确认。
- 供应商 166 家：归一化后 164 家；2 组仅括号全半角不同；另有 10 组“短名 vs 全称”。

## Goals / Non-Goals

**Goals:**

- 合同甲方成为一等数据，历史 638 份可自动归属，剩余可人工补。
- 下单提示、到期视图、期限登记都按“供应商 + 甲方”工作。
- 订购清单的甲方字段与主合同日期由所选甲方决定。
- 供应商名称在新导入中不再因空格、全半角产生重复。
- 存量重复在可控、可回退的前提下清理。

**Non-Goals:**

- 不引入第三家及以上的甲方管理界面（仍按“目录里有多少家就显示多少家”实现，只是当前播种两家）。
- 不重写合同模板填充、付款阈值、产品/图片数据结构。
- 不做模糊自动合并（错别字、简称一律人工确认）。
- 不改关页自动退出行为。
- 不做多人共享或服务端部署。

## Decisions

### 1. 甲方归属写入合同台账，而不是下单时临时推断

`contracts` 增加 `party_a`、`party_a_source`、`source_path`。导入时由解析器写入；历史数据由回填脚本写入。

备选：下单时按文件名或历史文本临时判断。问题是一次判断要扫全部合同，且无法人工修正、无法在到期视图复用，放弃。

同一份合同只属于一家甲方；不新增“合同-甲方”多对多表，避免过度设计。

### 2. 统计维度改为「供应商 + 甲方」，而不是在供应商行里叠加

新增 `supplier_contract_stats_by_party()`，按 `(supplier_name, party_a)` 聚合；`supplier_contract_stats()` 保留为兼容聚合。

到期视图按需拆行：同一供应商只有一家甲方时仍一行；两家都有时才两行；未确认甲方单独一行。这样既不丢信息，也不让列表无谓翻倍。

备选：继续按供应商取最晚止日，页面上再拆。问题是最晚止日的计算已经跨甲方，拆不出来，放弃。

### 3. 历史甲方按正文读取，按单号关联文件

回填脚本扫描合同目录，用文件名中的 `S\d{8}` 与 `contracts.contract_no` 关联；读取前 3 个表格 + 前 80 段，在两家公司全名中匹配。

两家名称同时出现时，按“购货单位/甲方/发包方/采购方/需方”标签后 80 字判断；都没有则标未确认。

备选一：按文件名含“兴趣岛/普惠”推断。问题是有误判风险，且用户明确要求按内容，放弃。
备选二：只处理 19 份仍可访问的旧路径文件。覆盖太低，放弃。

### 4. 甲方信息放后端 `party_a_profiles`，前端只读取

复用已有的 `party_a_profiles(name, payload)` 表，迁移时播种两家；新增 `GET /api/party-a` 与 `PUT /api/party-a`；系统状态页可编辑。

前端 `web/src/lib/party-a.js` 统一加载，`ContractPage` 与 `OrderPage` 共用；`localStorage` 只保留“上次选了哪家”和旧数据的首次迁移来源。

备选：继续用前端常量 + localStorage。问题是两家页面各存一份，容易漂移，且不符合“后端为主”，放弃。

### 5. 供应商名称以 NFKC 归一 + 去空白作为唯一键

新增 `app/domain/names.py`：

- `name_key(s)`：NFKC → 去所有空白（含 `　`）→ 去书名号/引号 → 小写。
- `clean_supplier_name(s)`：按标签截断 → 去内部空格 → 去首尾标点。

`suppliers` 与 `supplier_profiles` 增加 `name_key` 并建唯一索引；导入、档案保存、搜索都使用该键。

`repair_supplier_names()` 在每次启动时再执行一次归一与精确合并，幂等且只在发现重复时写入。这样即使 v4 升级后又被外部数据带入全半角重复，也会在下次启动自动清理，不必新增迁移版本。

备选：用 SQLite 自定义排序规则。问题是要重建索引、迁移复杂，且显示名仍可能不统一，放弃。

显示名保留“出现次数最多/合同最多”的写法（通常是全角括号），键只用于匹配。

### 6. 解析顺序：首部表格 → 右侧单元格 → 正文前部 → 文件名

`supplier_from_header(doc)` 以单元格段落为单位读取，避免 `cell.text` 把公司名与下一行标签黏在一起；取值后按标签截断，不再按空格切第一个词。

`.doc` 只在前 8000 字内查找，避免命中后文条款。

解析结果记录 `供应商来源`，用于导入报告与后续排查。

### 7. 存量去重：精确自动、近似人工

- 归一化后完全相同：迁移时自动合并（实测 2 组，166 → 164）。
- 短名与错别字：只生成候选清单，在系统状态页逐条确认（10 组）；“萌优”单独待定。
- 合并在单事务内完成，重挂 `supplier_products`、`contracts`、`historical_order_items`、`supplier_profiles`、`supplier_party_terms`、`product_supplier_names`，并写 `supplier_merge_log`。

不做拼音、编辑距离或大模型相似度自动合并，避免把不同主体并错。

### 8. 换供应商状态机放在下单页组件内

按“是否有产品 × 是否已导出”决定：

- 空单：直接切换。
- 有产品、未导出：每次切换都弹确认，文案明确会清空产品、单价和付款方式；确认后清空并切换，取消保留原供应商与全部已填内容。
- 有产品、已导出：视为一单结束，静默清空并切换。
- 页面刷新恢复供应商：直接赋值，不走切换逻辑。

`exported` 在导出成功后置 true；产品、单价/数量/备注、付款方式、甲方变更都会重新置 false。清空只处理订单内容与产品搜索框，保留预付款阈值与甲方选择；新供应商没有当前甲方合同时按 `autoPickParty()` 自动切到有合同的一家。

取消通过组件 `:key` 重挂把输入框恢复为原供应商，避免“输入框显示新名字、数据还是旧的”。`SearchSelect` 在已有选中项时额外发出 `edit` 事件：文本框一改成不同名称就立即走同一套确认，确认后只清空订单、暂不改变已选供应商，取消则重挂恢复文本。

### 9. 结构迁移与数据回填分开

- 结构迁移 v4：加列、建表、回填 `name_key`、合并精确重复、建索引。单事务、快、必做。
- `tools/backfill_party_a.py`：默认只读；`--apply` 才写库。依赖外部合同文件，可能耗时或被占用，单独执行、可重复运行。

这样迁移失败不会卡在 673 个 docx 的解析上；回填失败也不影响结构可用。

### 10. 接口形状

- `GET /api/suppliers` 每条增加 `parties` 数组；未确认甲方为 `party_a: ""`。
- `GET /api/party-a`、`PUT /api/party-a`。
- `GET /api/suppliers/duplicates`、`POST /api/suppliers/merge`。
- `/api/contracts/terms` 增加 `party_a`；`/api/contracts/expiry` 的每个 item 增加 `party_a`。
- 输出字段保持 snake_case，中文只出现在数据值中。

### 11. 关页退出保持现状

`alive.GRACE_SECONDS = 10`，最后一个页面关闭后约 10 秒退出。本次不调整。

### 12. 下单页沿用旧版供应商面板与甲方块

- 供应商搜索与“已选供应商”卡片并排；合同摘要用绿/黄/红/蓝底色卡片，按甲方分行显示最近签约与各自期限；整体“合同有效期”取所有已知甲方里止日最晚的一份。
- 数据新鲜度与“立即更新”放在摘要底部：状态来自 `GET /api/contracts/status`，更新走 `POST /api/contracts/sync`，前端轮询 `GET /api/contracts/sync`，完成后刷新目录、到期数据和当前供应商。
- 甲方信息块放在汇总卡底部，公司名称可切换，其余字段可编辑，失焦即 `PUT /api/party-a` 保存；导出的清单和主体合同使用同一对象。

备选：甲方信息只放在新增主合同页、下单页只显示名称。用户希望下单时能直接改并记住，放弃。

## Risks / Trade-offs

- **33 份合同读不到甲方、23 份没有源文件** → 统一进“未确认甲方”，倒计时页可筛选并单条指定；下单提示显示“未确认甲方”，不阻塞下单。
- **10 组短名可能并非同一主体** → 不自动合并，逐条人工确认；合并前备份。
- **合并会改变供应商数量与关系** → 事务内完成，产品数、合同数在验收时对比；保留合并日志。
- **到期视图行数与导航红点会变化** → 这是修正而非回归，验收时按新口径核对。
- **旧程序无法打开 v4 数据库** → 升级前自动备份，保留上一版发布包；回退用备份恢复。
- **名称带“玩县”等源文件错别字** → 新读取规则以文件正文为准；仍错的行由人工合并覆盖。
- **`.doc` 只能读前 8000 字** → 旧格式仅用于登记供应商与日期，不提取产品，风险可接受。
- **前端构建产物未更新** → 发布前运行 `npm run build`，并用 `build_release.py` 的时间戳校验兜底。

## Migration Plan

1. 运行 `tools/backfill_party_a.py`（只读），把可匹配数、甲方分布、未识别清单、重复组、预计影响交给维护者确认。
2. 迁移前自动备份为 `before_migration_v4`；执行结构 v4：加列、建表、回填 `name_key`、合并 2 组精确重复、建索引。
3. 执行 `tools/backfill_party_a.py --apply`，写入 `party_a`、`party_a_source`、`source_path`；未识别保持空。
4. 部署后端与前端，重建 `web/dist`。
5. 验收：产品 1053、合同 694 不变；供应商 164；甲方 638 有值；下单提示按甲方分行；导出两种甲方各一份比对；导入一份已收录合同不新增供应商；关页 10 秒退出。
6. 人工在系统状态页确认 10 组短名合并，“萌优”待定。

回退：恢复 `before_migration_v4` 备份 + 换回旧发布包。`data/` 不删除任何归档。

## Open Questions

无。甲方数量、历史甲方读取方式、合并策略、弹窗规则均已确认，剩余字段（如普惠地址）可在系统状态页后续补充，不影响规格与任务拆分。
